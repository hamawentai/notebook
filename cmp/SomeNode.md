# 进程

![image-20260214195524384](/Users/weix/Library/Application Support/typora-user-images/image-20260214195524384.png)

在 32 位 x86 架构下，虚拟地址空间为 4GB（0x00000000 到 0xFFFFFFFF），其中：

- **用户空间**：0x00000000 ~ 0xBFFFFFFF（约 3GB），供进程自身代码和数据使用。
- **内核空间**：0xC0000000 ~ 0xFFFFFFFF（约 1GB），由内核占用，进程无法直接访问，但内核会映射到所有进程的地址空间中，方便系统调用时切换。

**堆（Heap）**

- 增长方向：**向上**（向高地址）增长
- 用途：动态内存分配（如 `malloc` / `free`）
- 边界：`program break`（程序中断，图中红圈标注）是堆的当前顶边界，`brk()` / `sbrk()` 系统调用可以移动这个边界来扩展或收缩堆。

**未分配内存区**

- 位于堆和栈之间，是一段未映射的 “空洞”，防止堆和栈增长时过早碰撞。

**栈（Stack）**

- 增长方向：**向下**（向低地址）增长
- 用途：存放函数调用栈帧、局部变量、函数返回地址等
- 边界：栈顶（stack top）是当前栈的最高地址，每次函数调用压栈时，栈顶地址会减小。

***

在 Linux/x86-32 系统中，`0x00000000` 到 `0x08048000` 这段地址空间，通常是**保留未用的低地址区域**，也被称为**空指针陷阱区**。

1. **空指针保护**
   - 这段地址被刻意留空，不映射到任何有效内存。
   - 当程序出现空指针（`NULL`，值为 `0x00000000`）解引用等错误时，访问这段区域会直接触发**段错误（Segmentation Fault）**，让程序崩溃，从而快速暴露 bug，避免错误数据被执行或写入。
2. **防止低地址代码执行**
   - 这段区域通常被设置为不可执行，以缓解缓冲区溢出等攻击，防止恶意代码被加载到低地址执行。
3. **历史与约定**
   - 在传统的 Linux 链接器配置中，用户态可执行文件的默认加载基地址就是 `0x08048000`，因此从 `0x00000000` 到这个地址之间的空间都被保留，不用于存放程序代码和数据。

***

**内核空间是操作系统本身，不是你的 ELF 产生的。**

内核空间 = 内核代码 + 内核数据 + 内核栈。

内核在开机时加载，永久映射到 `0xC0000000 ~ 0xFFFFFFFF`。

你的 ELF 只占用户空间，和内核空间完全分开。

进程切换时：

- 用户空间换掉
- 内核空间永远不变，全局共享。

***

进程切换

1. **保存当前进程的 CPU 寄存器**
2. **切换页表（只换用户空间，内核空间不动）**
3. **恢复下一个进程的 CPU 寄存器**

**内核代码、内核数据、内核空间全程不变！**

1. 寄存器值保存在被换下进程的 `task_struct`（PCB）的 `thread` 结构体中，具体存在进程专属的内核栈里；
2. 这个区域位于内核空间的物理内存，全程由内核管理，不会随进程切换消失；
3. 恢复进程时，内核会把这些值从 PCB 中 “拷贝回” CPU 寄存器，进程就能无缝继续执行。

***

防止A进程不访问到B进程的空间

**页表隔离**：每个进程有独立的用户空间页表，只映射自己的物理内存；

**硬件强制**：MMU 翻译地址时会检查页表项的权限，越权直接触发异常；

**内核管控**：页表本身在内核空间，用户态无法修改，所有地址空间操作必须走内核系统调用

***

线程

| 场景                  | 能否访问？ | 底层原因                   |
| --------------------- | ---------- | -------------------------- |
| 同进程线程 A 读线程 B | ✅ 能       | 共用页表，地址映射一致     |
| 进程 A 读进程 B       | ❌ 不能     | 页表不同，MMU 拦截越权访问 |

总结：

1. 同一个进程的线程 A 拿到线程 B 的`int`指针，**可以直接读到值**，本质是线程共享进程的页表和地址空间；
2. 这种访问是 “无隔离” 的，甚至可以直接修改对方栈 / 全局 / 堆变量；
3. 唯一风险是目标变量的生命周期（比如栈变量被回收），而非 “权限问题”；
4. 这也是线程间通信比进程间通信（IPC）快的根本原因 —— 无需拷贝数据，直接访问地址即可。

LWP、进程、线程的区别

## 一、先给三个实体的**内核层面精准定义**

### 1. 进程（Process）

- 内核用 `task_struct`（进程控制块，PCB）描述进程的主线程；

- 进程是

  资源分配的基本单位

  ，拥有独立的 

  ```
  mm_struct
  ```

  （内存描述符），对应：

  - 独立的用户地址空间；
  - 独立的页表；
  - 独立的文件描述符表、信号处理、工作目录等资源；

  

- 进程的唯一标识是 `pid`（进程 ID），存储在主线程的 `task_struct->pid` 中。

### 2. LWP（轻量级进程，Light Weight Process）

- 内核用 `task_struct` 描述 LWP（和进程的主线程用同一个数据结构）；
- LWP 是**调度的基本单位**，是内核真正调度的实体；
- LWP**共享所属进程的 `mm_struct`**，即共享进程的地址空间、页表、文件描述符等所有资源；
- LWP 的唯一标识是 `tid`（线程 ID），存储在 `task_struct->tid` 中；
- 主线程的 `tid` 等于进程的 `pid`（内核用进程 ID 作为主线程的线程 ID，方便标识）。

### 3. 用户线程（User Thread）

- 由用户态线程库（如`pthread`）创建和管理，用 `pthread_t` 描述（用户态控制结构，内核完全不知道它的存在）；

- 用户线程是**用户态的逻辑执行流**，本质是线程库维护的栈、寄存器上下文等；

- 在 Linux/Windows 的

  一对一模型

  下，每个用户线程会绑定一个 LWP，用户线程的执行完全依赖对应的 LWP：

  - 用户线程的代码由 LWP 在用户态执行；
  - 用户线程的系统调用由 LWP 在内核态完成；
  - 用户线程的调度由内核调度对应的 LWP 实现。

  

------

## 二、三者的**内核关联机制**

### 1. 进程创建时的关联

- 执行 

  ```
  ./a.out
  ```

   启动进程时，内核会：

  1. 创建一个 `task_struct`（主线程的 LWP）；
  2. 创建一个 `mm_struct`（进程的地址空间），并将 `task_struct->mm` 指向这个 `mm_struct`；
  3. 主线程的 `tid` = `pid`（进程 ID）。

  

### 2. 用户线程创建时的关联

- 调用 

  ```
  pthread_create
  ```

   创建用户线程时，内核会：

  1. 调用 `clone()` 系统调用，创建一个新的 `task_struct`（子线程的 LWP）；
  2. 将新 `task_struct->mm` 指向当前进程的 `mm_struct`（共享地址空间）；
  3. 新 LWP 的 `tid` 是内核分配的唯一线程 ID，`pid` 等于进程的 `pid`；
  4. 线程库将用户线程的 `pthread_t` 和这个 LWP 的 `tid` 绑定，实现一一对应。

  

------

## 三、三者的**调度逻辑**

- 内核调度器只认 `task_struct`（LWP），不管是主线程还是子线程的 LWP，都是同等的调度实体；
- **进程切换**：调度到另一个进程的 LWP（`task_struct`），此时需要切换 `mm_struct`（修改 CR3 寄存器，刷新 TLB），因为不同进程的 `mm_struct` 不同，开销极大；
- **线程切换**：调度到同一个进程的另一个 LWP（`task_struct`），此时不需要切换 `mm_struct`（共享同一个 `mm_struct`），只需要切换寄存器和栈指针，开销极小。

------

## 四、用**内核数据结构佐证**

### 1. 进程的 `task_struct` 关键字段

```
struct task_struct {
    pid_t pid;          // 进程ID
    pid_t tid;          // LWP ID（主线程tid=pid）
    struct mm_struct *mm; // 指向进程的地址空间
    int nr_threads;     // 进程拥有的LWP数量（对应ps的NLWP）
    // 其他字段...
};
```

### 2. 共享地址空间的证明

- 进程的主线程和子线程的 `task_struct->mm` 指针指向同一个 `mm_struct`；
- `mm_struct` 包含页表基地址（`pgd`），所以所有 LWP 共享同一个页表，切换时不需要换页表。

## 五、对应到 `ps -efL` 命令的输出

```
UID        PID  PPID   LWP  C NLWP STIME TTY          TIME CMD
user     12345  12300 12345  0    3 10:00 pts/0    00:00:00 ./thread_example
user     12345  12300 12346  0    3 10:00 pts/0    00:00:00 ./thread_example
user     12345  12300 12347  0    3 10:00 pts/0    00:00:00 ./thread_example
```

- `PID=12345`：进程的 `pid`，所有 LWP 的 `task_struct->pid` 都等于这个值；
- `LWP=12345/12346/12347`：LWP 的 `tid`，对应 `task_struct->tid`；
- `NLWP=3`：进程的 `task_struct->nr_threads`，即进程拥有的 LWP 数量；
- 三行输出对应三个 `task_struct`（三个 LWP），都属于同一个进程。

------

## 六、终极技术总结

1. **进程是资源容器**：由 `task_struct`（主线程）和 `mm_struct`（地址空间）组成，负责分配资源；
2. **LWP 是调度实体**：是 `task_struct`，共享进程的 `mm_struct`，是内核调度的最小单位；
3. **用户线程是用户态包装**：由线程库管理，一对一模型下和 LWP 一一对应，通过 LWP 获得 CPU 执行权；
4. **关系**：一个进程包含多个 LWP（一对多），每个 LWP 对应一个用户线程（一对一），内核调度 LWP 实现线程执行，共享进程资源。

你之前学的「线程切换不换页表」「进程切换换页表」，本质就是：

- 线程切换：同一个进程的 LWP 切换，共享 `mm_struct`，不需要换页表；
- 进程切换：不同进程的 LWP 切换，需要切换 `mm_struct`，开销极大。
